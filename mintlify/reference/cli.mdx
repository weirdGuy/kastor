The current CLI command is `kastor`.

```bash
kastor <command> [flags] [dir]
```

Most commands default to the current directory when `[dir]` is omitted.

## `kastor init`

Scaffold a new module that passes `kastor validate` and `kastor build` with zero edits.

```bash
kastor init [--target name] [--force] [dir]
```

Example:

```bash
kastor init demo
```

The scaffold is six files: `kastor.hcl` (a model and a codegen target), one `.agent`, one `.tool`, one `.prompt`, `mcp_servers.json`, and a `README.md`. The tool binds to the reference MCP fetch server (`uvx mcp-server-fetch`, declared in `mcp_servers.json`), so the generated project runs without writing any code. Output is deterministic: the same Kastor version always produces a byte-identical scaffold.

Flags:

| Flag | Meaning |
| --- | --- |
| `--target` | Codegen target to pre-configure. Only `langgraph` (the default) has a scaffold; `eve` is a usage error here even though `kastor build` supports it. |
| `--force` | Scaffold into a non-empty directory. Only the scaffold's own file names are overwritten; everything else is kept. |

A directory that already contains visible files is refused with exit code `2`. Hidden entries such as `.git` never block scaffolding, so `kastor init` works in a freshly created git repository.

## `kastor validate`

Parse, type-check, resolve references, check prompt variables, and build the dependency graph.

```bash
kastor validate [dir]
```

Example:

```bash
kastor validate examples/weather
```

This command produces no generated files and does not touch state.

## `kastor build`

Generate framework code from codegen targets.

```bash
kastor build [--target name] [dir]
```

Examples:

```bash
kastor build examples/weather
kastor build --target langgraph examples/weather
```

Implemented targets:

| Target label | Status |
| --- | --- |
| `langgraph` | Implemented. Generates a Python LangGraph project. |
| `eve` | Implemented. Generates a Vercel eve project (TypeScript). |

There is no implemented `kastor compile` command. Use `kastor build`.

### Generated output is disposable — with one exception

`kastor build` owns its output directory. It rewrites the files it generates,
deletes visible files it no longer generates, and refuses to touch a non-empty
directory that has no `.kastorbuild` marker. Hidden entries (`.venv`, `.eve/`,
`.env.local`) are always left alone.

The exception is a tool with `kind = "runtime"`. Its body is your code, so the
generated stub is written **once** and then belongs to you:

| State of the file on disk | What the next build does |
| --- | --- |
| Missing, or still byte-identical to the stub kastor wrote | Writes or regenerates it |
| You edited it, spec unchanged | Leaves it alone, silently |
| You edited it, spec changed the tool | Leaves it alone; writes the new stub to `<name>.kastor-new` beside it and says so, once |
| You edited it, tool removed from the spec | Keeps the file instead of deleting it, and says so, once |
| You reverted it to the current stub | Takes ownership back and removes the sidecar |

So implement the stub in place — you no longer need to keep the real logic in a
separate file and call into it.

A `.kastor-new` sidecar is a plain file, deliberately visible, and inert to
Python and TypeScript because of its suffix. It is the build telling you the
generated interface moved underneath your implementation: diff the pair, carry
the change into your file, then delete the sidecar.

```bash
kastor build examples/scheduler
# kastor: target.langgraph: 1 generated stub changed under your implementation; your files were kept:
#   gen/langgraph/tools/create_draft.py — new stub: gen/langgraph/tools/create_draft.py.kastor-new
#   fix: diff each pair, carry the change into your file, then delete the .kastor-new file

diff gen/langgraph/tools/create_draft.py.kastor-new gen/langgraph/tools/create_draft.py
```

These warnings go to stderr and do **not** fail the build: the code was
generated and synced, so `kastor build` still exits `0`.

Ownership is tracked in the `.kastorbuild` marker at the root of the output
directory. Deleting it is safe but forgetful — with no record, kastor can no
longer tell its own untouched stub from your implementation, so it treats every
existing file as yours.

## `kastor plan`

Compare the spec, state file, and remote platform for platform targets.

```bash
kastor plan [--target name] [dir]
```

Example:

```bash
kastor plan examples/weather
```

`plan` is a pure read. It should not modify remote resources or write the state file.

Implemented provider:

| Target label | Status |
| --- | --- |
| `memory` | Implemented. Ephemeral in-memory provider for local demos and tests. |

Planned provider:

| Target label | Status |
| --- | --- |
| `claude_agents` | Planned for v0. Claude Managed Agents is the selected provider; nothing registered in the current CLI yet. |

## `kastor apply`

Plan and reconcile platform targets.

```bash
kastor apply [--target name] [dir]
```

Example:

```bash
kastor apply --target memory examples/weather
```

`apply` does not prompt for confirmation in v0. State is saved after completed operations.

## `kastor destroy`

Delete all resources tracked in state for selected platform targets.

```bash
kastor destroy [--target name] [dir]
```

`destroy` deletes resources in reverse dependency order and updates state after each deletion.

## `kastor fmt`

Canonically format Kastor HCL files.

```bash
kastor fmt [--check] [--diff] [dir]
```

Files formatted:

- `.agent`
- `.tool`
- `.kastor`
- `kastor.hcl`

Prompt files are left untouched because the body is preserved byte for byte.

## `kastor version`

Print the CLI version and the commit it was built from.

```bash
kastor version
```

```console
kastor version 0.1.0 (commit 1a2b3c4)
```

Release binaries stamp both values at build time; `go install` builds report the module version and VCS revision from Go build info, and untagged source builds fall back to `dev`.

| Surface | Status |
| --- | --- |

## Exit codes

The design spec defines:

| Code | Meaning |
| --- | --- |
| `0` | Clean run. |
| `1` | Validation, codegen, plan, or apply error. |
| `2` | Usage or IO error, including state lock contention. |
